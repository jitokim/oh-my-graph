### Added

- **A run paused on a usage limit now says why: `runs list`, the pause hint and `resume --approve/--reject` name the limited nodes and the CLI's message.** The scheduler writes a run-level `limit_pause` record to `state.json` once, at the end of the leg that hit the limit (`node_ids`, sorted; `cause`, the first limited node's message exactly as the runtime printed it; `at`, when the pause was taken), beside the gate pause, and a resumed leg's first snapshot write clears it, as it clears `gate.paused_at`. A leg that pauses on a limit and at a gate keeps both records. `runs list` prints `paused on a usage limit at <node ids>: <cause>` under a `PAUSED` row's hint; the end-of-leg hint reads `Session limit reached (resets <time>): <cause>` when the message names a reset time, and `Session limit reached: <cause>` when it does not, with the resume command unchanged; and `resume --approve`/`--reject` on such a run refuses with `is paused on a usage limit at <node ids>: <cause>, not at a gate (resume it with --retry-failed)` instead of "is not paused". Every one of these passes the cause through `fence.SanitizeTerminalLine` and leaves it off when none was captured. The record is display only and optional (absent when a run never hit a limit, a failed write only warns): the status is still `PAUSED`, `runstatus` does not read it, `resume` re-launches the same nodes, every exit code is unchanged (`runs list --exit-in-flight` included), and the schema stays 3, since an older binary ignores the key. This is ADR 0031 §3.5 only; the `loop` supervisor (§3.1–§3.4, §3.6) is still Proposed. ([#358](https://github.com/jitokim/oh-my-graph/issues/358))
