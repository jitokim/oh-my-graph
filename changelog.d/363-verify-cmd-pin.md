### Security

- **The work under test can no longer relax `--verify-cmd` by editing the script it executes: a pinned script that changed fails the verification instead of passing it.** Once per `auto` invocation, before the starting-tree baseline, each command of the `--verify-cmd` line (split on `&&`, `||`, `;`, `|`) pins the one file it executes, resolved against the invocation directory with every symlink followed: past leading `NAME=value` words and the wrappers `env`, `exec`, `command`, `nice` and `time`, an interpreter (`sh`, `bash`, `zsh`, `dash`, `python`, `python3`, `python3.N`, `node`, `ruby`, `perl`) pins nothing when the command holds `-c` or a runner or inline mode (a shell's short-option cluster holding `c`, such as `-ec`; `node`'s `--test`, `-e`, `--eval`, `-p` or `--print`; a python's `-m` before its first file), else its first following argument that is an existing readable regular file and nothing after it; any other command word is pinned only if it is written as a path (`./check.sh`). The interpreter binary and a bare name found on `PATH` are never pinned. Each pin is the word, its absolute path, and the SHA-256 of its content. The plan screen lists every pinned path under the build-evidence block, or warns `verify-cmd has no pinned script` when there is none. Immediately before and immediately after every engine-run verification of that command (the baseline and every cycle's sinks), each pinned file is resolved and hashed again, and a changed digest, a re-pointed path, or a file gone or unreadable is a verify fault naming the file's absolute path (`... changed since launch: pinned file <path>`), never a PASS; at the baseline that is a red baseline, exit 5. A change found after the command ran, when the check before it passed, says `... changed while the command ran — is this a file the command itself writes? pinned file <path>` instead. The pins are written to `state.json` as an optional `verify_pins` array (`word`, `path`, `sha256`; absent without `--verify-cmd` or when the line executes no pinnable script, schema stays 3), and `resume` re-checks the recorded pins rather than taking new ones. There is no re-pin flag: to accept a deliberate change, start a new run. Only the executed script is pinned — not an inline `-c` script or a runner or inline mode such as `python -m pytest`, not a script fed on stdin (`sh < check.sh`), not what runs behind a wrapper given options (`nice -n 10`, `env -i`), not what a script sources, reads or writes, not the `Makefile` behind `make verify`, not the tests `go test` runs, not a path that only resolves after a `cd` inside the command — and an edit made and reverted while the command runs is not seen (docs/LIMITATIONS.md). Pinning only the executed script also fixes the earlier pin-every-named-file rule faulting every run of `sh check.sh | tee log.txt` or `pytest --junitxml log.txt` on the file the command itself rewrote ([#367](https://github.com/jitokim/oh-my-graph/issues/367)). Hand-written `run` graphs and `internal/schedule` are unchanged. ([#363](https://github.com/jitokim/oh-my-graph/issues/363))
