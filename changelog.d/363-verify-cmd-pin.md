### Security

- **The work under test can no longer relax `--verify-cmd` by editing the files it names: a pinned file that changed fails the verification instead of passing it.** Once per `auto` invocation, before the starting-tree baseline, every word of the `--verify-cmd` line that resolves against the invocation directory, every symlink followed, to an existing readable regular file is pinned: the word, its absolute path, and the SHA-256 of its content. Immediately before and immediately after every engine-run verification of that command (the baseline and every cycle's sinks), a decorator around the engine's verifier resolves and hashes each pinned file again, and a changed digest, a re-pointed path, or a file gone or unreadable is a verify fault naming the file's absolute path (`... changed since launch: pinned file <path>`, or, for a change made while the command ran, `... is this a file the command itself writes? pinned file <path>`), never a PASS; at the baseline that is a red baseline, exit 5. The pins are written to `state.json` as an optional `verify_pins` array (`word`, `path`, `sha256`; absent without `--verify-cmd` or when the line names no file, schema stays 3), and `resume` re-checks the recorded pins rather than taking new ones. There is no re-pin flag: to accept a deliberate change, start a new run. Only files named on the command line are pinned — not what a script sources, not the `Makefile` behind `make verify`, not the tests `go test` runs, not a program on `PATH` — and an edit made and reverted while the command runs is not seen (docs/LIMITATIONS.md). Hand-written `run` graphs and `internal/schedule` are unchanged. ([#363](https://github.com/jitokim/oh-my-graph/issues/363))
