**Disposition: ANSWERED-NO**, recorded as an ADR rather than only as a comment: [`docs/adr/0039-a-gate-is-authored-not-attached.md`](docs/adr/0039-a-gate-is-authored-not-attached.md), commit `fd33c74`, with an entry under `## [Unreleased] → ### Documented` in `CHANGELOG.md`. Shape 1 is refused. Shapes 2, 3 and 4 are **not** decided here — §6 says so explicitly, and they stay open.

The record is where the reasoning lives, so that a future reader meets it without finding this thread. What follows is the short form of it.

### What is not in dispute — @jihoon-lbox

The want is accepted. The measurement is accepted. So is the diagnosis: the ergonomic gradient selected the mode with no evidence, run after run, and the compensating labour is exactly the labour the tool exists to remove. Nothing below argues that the combination is unreasonable to want.

Two of your arguments survive this refusal intact, and the ADR says so before refusing:

- **The parallel with `--verify-cmd` holds further than a quick reading suggests** (§1.2). `--verify-cmd` does not name a node either: the operator supplies one string and trusted code finds the attachment points itself (`internal/coordinator/verifycmd.go:250-259`). So the chicken-and-egg that killed the per-node form in ADR 0033 — *"Node ids are invented by the planner, so the mapping cannot be authored before the plan exists"* (`docs/adr/0033-the-run-is-the-unit-of-evidence-not-the-node.md:501`) — does **not** apply to `--gate-before-sink` as you posed it. A structural attachment point needs no node id. Any refusal leaning on chicken-and-egg would be refusing a proposal you did not make, so this one does not lean on it.
- **The strongest argument in the issue is the ergonomics, and it is untouched** (§3). The path that exists routes through a saved `graph.json`, not YAML (`generatedSpecFileName`, `cmd/oh-my-graph/main.go:1135`). "Edit the generated JSON" is precisely the gradient you measured.

### Why the mechanism is refused anyway

The parallel stops at what the two attachments *are*. `--verify-cmd` sets a field on nodes that already exist: same nodes, same edges, same sinks. A gate changes the topology, and it changes it into a shape three separate parts of the system already have opinions about.

1. **A gate ends the leg; it does not block it.** oh-my-graph is a stateless CLI with no daemon, so `Scheduler.Run` drains in-flight siblings, writes the pause snapshot and returns `*PausedError` (`internal/schedule/scheduler.go:720-730`), which the CLI maps to exit 2 (`cmd/oh-my-graph/main.go:138-141`); ADR 0003 decided this. Attaching a gate is therefore not "one more field trusted code may set" — it is trusted code deciding that **this run stops**, on a graph nobody read.
2. **It cannot coexist with `--verify-cmd` at a sink.** The attach loop skips gate nodes (`internal/coordinator/verifycmd.go:252`), and a graph whose sinks are all gates is refused outright: *"graph %q ends in gate node(s) only, so the verify command has nowhere to attach: a gate's PASS is a human decision with no subprocess for an evidence command to be evidence about"* (`internal/coordinator/verifycmd.go:262`). Your issue asks for evidence **and** a gate; attaching the gate upstream of every sink puts the gate exactly where the evidence command needs a subprocess and finds none.
3. **It collides with the loader on plans the planner is invited to write.** `handoff: session` with a gate parent is rejected (`internal/graph/validate.go:663`), and a gate inside a feedback body is rejected because *"replaying its recorded decision on a later round would silently re-approve work the human never saw"* (`internal/graph/feedback.go:191`). The planner is invited to use both shapes, so post-validation insertion can turn a legal plan illegal, or — worse — legal-but-wrong.
4. **It parks an unattended run in a state the documented supervisor loop reads as finished.** `cmd/oh-my-graph/main.go:26-34` publishes `until oh-my-graph runs list --exit-in-flight >/dev/null; do sleep 30; done` as the contract. The plan-time refusal at `internal/coordinator/coordinator.go:1052` exists for that reason, stated at `:957`: *"an unreviewed auto-plan could park the run awaiting an approval nobody knows to give, forever."* `auto` today has one pause class; a gate would add a second, whose exit shape a supervisor cannot distinguish from done.

### What to do instead — §3 of the ADR, with its cost stated

1. `oh-my-graph auto "<goal>" --plan-only` — the planner runs, no node does, the spec is kept (`cmd/oh-my-graph/main.go:759-772`).
2. Edit that spec: add `type: gate` with its `depends_on` (three lines; the shipped example is `approve-merge` at `graphs/merge-shepherd.yaml:764-766`, the only `type: gate` in `graphs/`), and put `success_check.verify` on whichever nodes you want the engine to check.
3. `oh-my-graph run <path>` — the printed command at `main.go:766-769`.

Two frictions, both real and both named in the record rather than glossed: the spec is JSON, not YAML (`main.go:1135`), and `resume` refuses `--verify-cmd` on a hand-written graph (`checkVerifyCommandApplies`, `cmd/oh-my-graph/resume.go:306-322`) — nothing is lost there, since the graph's own `verify:` round-trips untouched, but a user who learned the flag on `auto` will meet a refusal on the resumed leg of the graph they were just told to write.

### One correction to a premise, and what stays open

Your shape 2 says `graphs/fragments/gated-lane.yaml` "already carries `dev → e2e → review → pr` with the gating pair". The wiring is there, but the fragment's "GATE PAIR" is a narrowed `success_check` plus a `feedback:` arc back to the implementer (`graphs/fragments/gated-lane.yaml:15-20`) — it is not a `type: gate`. In all of `graphs/`, `type: gate` appears once, at `graphs/merge-shepherd.yaml:765`. That does not weaken shape 2; it means shape 2 is adding a gate to that lane, not surfacing one it already has.

Shapes 2, 3 and 4 are undecided, not refused (ADR 0039 §6). Shape 3 in particular — collapsing N `--input k=v`, via `--input-file` or a defaults block the graph declares — attacks the reason you gave for preferring `auto` in the first place, needs no engine seam, and is orthogonal to everything above. If you file it on its own it will be judged on its own; it is the one I would open next.
