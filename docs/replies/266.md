### The workaround — `docs/LIMITATIONS.md:98-104`

The scrub matches the **whole** variable name, so a key carried under a different one survives, and your command can map it back inside its own shell:

```yaml
verify: { command: "OPENAI_API_KEY=$TEST_OPENAI_KEY make test" }
```

Know what that buys before doing it. Any provider CLI that command goes on to reach then runs on API-key authentication and is billed to the API, which is the thing the scrub exists to prevent. For the four tests you describe this is safe — they assert a key is *set*, they do not spend it. For a `verify:` that shells out to `claude` or `codex`, it is not.

### Why shapes 1 and 2 are refused — @jihoon-lbox

Your framing is right about the threat model and wrong about one fact, and that fact is what decides it. You write that "a verify command has no login to protect — it is `sh -c`, run by the engine, on the user's own machine". The second clause is true; the first does not follow from it. `verify: { command: "claude -p ..." }` is legal, and is named as legal at `DESIGN.md:1504`. A verification command may itself invoke a provider CLI, and a repo's own git hooks or `make` targets may reach one without the graph's author knowing they do. So scoping the scrub to the runtime child (shape 1) does not withdraw a protection from something that has no login. It withdraws it from a class of commands that sometimes does, on the basis of a property — "this one is only a test suite" — that the engine cannot read off the command string.

Shape 2 (`inherit_env: [OPENAI_API_KEY]`) is the better-designed of the two, and it is refused for a different reason: it is a second place the list has to be right. The policy today is one list with no branch — a single `scrubbedVars` in `internal/childenv/childenv.go`, no per-seam fork and no per-runtime fork. The failure mode that buys is specific and quiet: when a fifth provider variable is added, any half that falls behind bills silently, and nothing fails to say so. A per-verification opt-in adds exactly such a half. The remap above buys you the same outcome with no new schema key and no second list, and it is just as visible in the graph as `inherit_env` would have been.

Neither of those is "by design" offered as an answer. The design is a decision with a cost; you paid the cost; and the part that was actually wrong is that nothing anywhere said so.

### Shape 3 is not built, and it is the one worth keeping open

You called it the cheapest and useful even if 1 or 2 land. That is right, and it is still not in this commit. The obstacle is mechanical rather than principled, and you can check it:

- A failure Detail is capped at 240 runes (`maxDetailRunes`, `internal/schedule/scheduler.go:82`) and the cap keeps the **tail** (`capDetail`, `:89`). An unconditional sentence would eat 100-odd runes of the pytest output that is the reason anyone reads the row.
- Making it conditional — append only when a scrubbed name appears in the command's output — requires the verify seam to report that it happened, which is a new field on `verify.Result` and a widening of that seam.

So it is a real change with a real design question behind it, and it is recorded as not-fixed rather than declined. Concretely, this means the FAIL row in your terminal still says nothing about the environment, and you would still have to find `docs/LIMITATIONS.md` yourself. That is the residual this fix leaves you, and I would rather name it than let the FIX label imply otherwise.
