1. THE STATED ASSUMPTION
------------------------------------------------------------------------------

ASSUMED GRANT-MATCHING RULE (not authoritative — see grantMatches(), one function,
change it in one place):

  * A grant "Bash(P)" applies only to Bash calls. Non-Bash grants (Read, Grep,
    Glob, Skill, ...) never match a sub-command.
  * If P ends in " *", the part before it is a TOKEN PREFIX. "Bash(go *)" matches
    a sub-command whose first token is "go". "Bash(gh pr *)" requires the first
    TWO tokens to be "gh" then "pr". The "*" covers all remaining arguments and
    is not matched character-wise.
  * P == "*" matches every sub-command.
  * P with no "*" is an EXACT whole-command match: "Bash(ls)" matches the
    sub-command "ls" and nothing else.
  * A bare grant "Bash" with no parentheses matches EVERY sub-command.
  * Matching is on tokens, never on the raw string, so quoting and spacing in the
    arguments cannot change the verdict.

WHAT THIS RULE DELIBERATELY DOES NOT MODEL, because it is unknown:
  * whether the real matcher splits a compound command at all, or matches the raw
    shell string against the pattern as one unit;
  * whether an unmatched later sub-command denies the whole call;
  * whether a working-directory / sandbox constraint is applied to path arguments
    IN ADDITION to the pattern (§9 gives evidence that something path-sensitive
    is operating, but not what);
  * whether a denial arises from failure-to-match, an explicit deny rule, or a
    sandbox check. The denial text is identical in all three cases.

WHAT THE REPOSITORY DOES PIN DOWN (measured, not from source — DESIGN.md):
  * DESIGN.md:106-110 — "A tool call is matched against every loaded permission
    rule; if nothing matches, the call resolves to *ask*, and the mode decides
    what an unanswerable ask becomes — under dontAsk (our unattended default) it
    becomes a deny." So a planned node is DEFAULT-DENY, and "denied" means "no
    rule matched" — indistinguishable on disk from an explicit deny or a sandbox
    refusal.
  * DESIGN.md:113-116 — "--disallowedTools subtracts and beats a prior allow, but
    only at bare-tool-name granularity (Bash); a scoped deny like Bash(*) matches
    a command literally starting with * and enforces nothing. Measured on claude
    2.1.220." A bare "Bash" in a node's disallowed_tools therefore beats every
    allow it holds; §6 counts how many denied calls sat under one.
  * DESIGN.md:2195-2199 — --tools bounds tool NAMES and not SCOPES, and a grant
    can be invisible in graph.json while its durable record is state.json's
    tool_policies. §6 cross-checks the two records against each other.

It holds its port for as long as it runs and keeps serving the tree it was compiled from while `bin/oh-my-graph` is rebuilt underneath it, so a stale server renders a stale build label and a reader cannot tell it from a current one. The footer has named the build since v0.5.2, but only for a human: settling "is this the build I just made" meant scraping prose out of the page body.\n\nThis PR exposes the build that `internal/serve/build.go` already computes in a form a machine can read.\n\n## The decision, and why\n\n**`<meta>` tags in the page head**, beside the gate token already rendered there. `internal/serve/build.go` grows a `Build` struct (`Version`, `Revision`, `BuiltAt`, `Label`) produced by one constructor, `serve.CurrentBuild(version)`. `BuildLabel` is now the `Label` field of that same value rather than a second rendering of the same facts, so the footer prose and the head tags have exactly one author and cannot disagree. `Server.WithBuild` and `Dashboard.WithBuild` now take a whole `Build` instead of a label string, and both templates render through a single `pageData` type, so a field added for one template either reaches both or fails to compile, rather than becoming a template evaluation error (a 500 on the page) at request time.\n\n```console\n$ curl -s http://127.0.0.1:8642/ | grep omg-\n<meta name="omg-token" content="…">\n<meta name="omg-version" content="0.10.0">\n<meta name="omg-revision" content="56e64fb-dirty">\n<meta name="omg-built-at" content="2026-08-20T00:53:55&#43;09:00">\n```\n\nThe alternative was a JSON endpoint. JSON is easier to script against: no HTML to parse, and no attribute escaping to undo. It was not chosen because a `<meta>` tag costs nothing and rides a page the browser already fetched, while an endpoint is one more route to keep — one more thing to version, to hold inside the loopback guard and the security headers, and to keep answering identically on both surfaces. For a fact already being rendered into every page, the extra route buys convenience and adds surface. A JSON endpoint can still be added later over the same `Build` value without changing anything here.\n\n## The fields, and why the version alone is not enough\n\n| tag | content |\n| --- | --- |\n| `omg-version` | the exact token `oh-my-graph version` prints after the program name, with any leading `v` trimmed, so comparing two servers is a string equality rather than a parse |\n| `omg-revision` | the short VCS revision the toolchain stamped, with the `-dirty` marker when set |\n| `omg-built-at` | the mtime of the running executable, RFC3339 in local time, so two of them order |\n\n**The version alone cannot settle which build is answering.** Every build between two tags carries the same version, so a week-old process and the one built this afternoon both say `v0.5.2`. Two builds of one version are told apart by the commit and by the build time. Both atoms are needed, not either one: the revision is absent more often than it looks (a `-buildvcs=false` build, a proxy module build, a build from a linked git worktree, which is how the graph lanes of this project build), while the mtime moves on every rebuild, stamp or no stamp.\n\n`omg-built-at` comes off the same single, once-per-process stat that the footer label reads (`sync.OnceValue`), so nothing reports two different build times for one process, and a rebuild underneath a live server does not rename the build that is answering.\n\nAll three tags are **always emitted**: empty content means unknown (no VCS stamp, or an executable that could not be stat-ed), while a tag missing entirely means a server older than this change, which is itself an answer.\n\n## Both surfaces are covered\n\nThe dashboard (`GET /{$}`, `ui/dashboard.html`) and the single-run view (`ui/index.html`) — the latter both standalone (`serve <run-id>`) and mounted under the dashboard at `/run/<id>/`.
